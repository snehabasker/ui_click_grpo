# serving/: serving the trained click policy under agent-style traffic

Goal: take the LoRA policy from the main project, serve it, and measure what each serving technique buys, with
reproducible raw logs and an accuracy check after every change. A speed-up that changes click accuracy is reported as a
failure, not a win.

Nothing under `serving/` changes training code or the published results in `../results/`.

## Status

| Phase | What | Status |
|---|---|---|
| 0 | Merge adapter, verify it, trace generator, load client, tests | **done** (this document) |
| 1 | vLLM vs SGLang on the same checkpoint | **done, with caveats** (see Phase 1 results and the follow-up on SGLang's configuration) |
| 2 | Prefix-aware router in Rust | **done, with a mixed result** (see Phase 2 results: the routing works, the latency benefit is not clear) |
| 3 | Fused RMSNorm + INT8 quantisation Triton kernel | **done, as a standalone operator** (see Phase 3 results: not integrated into an engine, no end-to-end claim) |
| 4 | Prefill/decode disaggregation (time-boxed) | **attempted on one GPU, with an analytical estimate**: works at 1 and 4 clients, fails at 16 with default settings (see Phase 4 results); not a two-GPU result |
| 5 | TensorRT-LLM (time-boxed) | not started |

Hardware: one RTX 5050 Laptop GPU (8 GB, compute capability 12.0, driver 592.82, CUDA 13.1 as reported by the driver),
Windows 11, 23.6 GB RAM. Engines run inside WSL2 Ubuntu (WSL 3.0.3, kernel 6.18, 11.7 GB of RAM visible to Linux).

## Phase 0 results

### 1. The merged checkpoint clicks like the adapter model

The LoRA adapter (`runs/clean/adapter`) was merged into the bf16 base weights, so every engine loads one plain checkpoint
(`merged-clean`, model hash `f4945dbb7c5b459fe0cce1b78362bff134b12a4a15108e9342c8c6b3a1d0de7f`). Both models were run through the
same HF code path, greedy, on the two fixed sets. Pass criteria were fixed before looking at results: accuracy within 2.0
points **and** an exact paired sign test with p > 0.05.

| set | adapter model | merged model | delta | only adapter / only merged correct | sign test p | verdict |
|---|---|---|---|---|---|---|
| synthetic held-out (n = 300) | 63.33% [57.7, 68.6] | 63.33% [57.7, 68.6] | +0.00 pts | 2 / 2 | 1.000 | pass |
| ScreenSpot subset (n = 400) | 53.25% [48.4, 58.1] | 53.75% [48.9, 58.6] | +0.50 pts | 3 / 5 | 0.727 | pass |

Accuracy is preserved, but the clicks are **not bit-identical**, because the merge rounds the LoRA delta into bf16 weights:

| set | identical click point | median shift | 90th percentile shift | largest shift |
|---|---|---|---|---|
| synthetic | 58.3% | 0 | 10 units (1.0% of the image side) | 98 units |
| ScreenSpot | 54.9% | 0 | 18.8 units (1.9%) | 725 units |

(units: the model's 0-1000 coordinates, worst axis, over items where both models returned a valid point.) A handful of items
move a long way in either direction (hit -> miss and miss -> hit both occur), and they cancel in the totals. This is a
reason to keep the accuracy check after every later change rather than assume equivalence.

The adapter model also reproduces the published numbers on the re-rendered images: 63.33% (190/300) on the synthetic set,
identical to `../results/eval_clean.json`, and 53.25% (213/400) on ScreenSpot against the published 53.2%.

Raw: `results/raw/merge_verify_20261026-004301.json`, `results/raw/merge_diff_20261026-004333.json`,
`results/raw/merge_info_clean.json`.

### 2. The agent trace

`serving/traces/default` (96 sessions, seed 0), generated by `scripts/gen_traces.py`:

| property | value |
|---|---|
| sessions / requests | 96 / 560 (3-8 turns per session) |
| sessions sharing a prefix | 72 (75%), over 4 shared prefixes with skewed popularity (33 / 18 / 12 / 9 sessions) |
| the other 24 sessions | a unique prefix each (differs from the first characters) |
| shared prefix | system prompt + 2 few-shot screenshots with their answers |
| history | previous instructions and answers as text (no old screenshots) |
| first turn incl. shared prefix | 1,666 tokens |
| a bare single-screenshot request | 412 tokens |
| shared prefix (difference of the two) | about 1,254 tokens, i.e. roughly 75% of a first-turn request is cacheable |

Token counts come from the real Qwen2-VL processor (`traces/default/token_stats.json`), not an estimate. The "bare request"
count uses the raw instruction without the fixed answer-format sentence, so the prefix figure is approximate.
Replays are identical across engines: the assistant history in every request is the ground-truth click, not the model's own
answer. Seeds are disjoint from training (< 1e6) and from the held-out test splits (>= 1e7).

Important: the policy was trained zero-shot with one screenshot. The trace adds a system prompt, few-shot turns and history,
which the policy never saw. Click accuracy *on the trace* is therefore reported separately from the zero-shot accuracy checks
and may differ; that is measured in Phase 1, not assumed here.

### 3. Load client and validation

`servebench/client.py` streams every request and records time-to-first-token, inter-token gaps, end-to-end latency, tokens
(from the engine's `usage`), throughput, click accuracy on the trace, GPU memory and utilisation (nvidia-smi, 0.5 s), and the
engine's prefix-cache counters from `/metrics` where they exist. Failures (timeouts, 5xx, resets) are recorded, never raised.

Its inter-token timing was checked against a raw-socket server with exact (busy-wait) spacing. Median gap, 72 gaps per row,
0 request errors:

| true spacing | raw-socket reader | this client |
|---|---|---|
| 10 ms | 10.03 ms | 10.03 ms |
| 20 ms | 20.06 ms | 20.05 ms |
| 40 ms | 40.08 ms | 40.10 ms |

So inter-token numbers from this client can be trusted in the 10-40 ms range where decode steps on this GPU are expected to
fall. (On this Windows machine `asyncio.sleep(3 ms)` actually sleeps 15.95 ms in that run, which is why the mock server cannot
validate small intervals.) Raw: `results/raw/client_timing_20261026-004655.json`. How this was found is in `NOTES.md`.

25 tests (`pytest serving/tests`) cover statistics, manifests and tamper detection, environment capture, trace determinism and
prefix sharing, message construction, and the client against a mock server. **The mock server only tests plumbing: no number
from it is ever reported** (its output files are prefixed `MOCK_`).

### Why: what is measured, what the logs show, and what is only a guess

**Measured.**
* Both caches work and hit about equally by volume (66-67% of prompt tokens). So the engines differ in *what they do with* a hit,
  not in whether they get one. (SGLang's own log agrees; see below. The shared prefix is about 1,250 tokens, from
  `traces/default/token_stats.json`.)
* For vLLM the cache is worth a lot at every concurrency: with it off, each request recomputes the whole prompt, which is
  1,666 tokens on a first turn.
* For SGLang the cache helps at c=1 and c=4 and does nothing or hurts at c=16 (throughput 1.60 -> 1.40, TTFT 5.57 -> 8.63 s).
* vLLM's time to first token stays low at c=32 with the cache on (2.03 s) but its inter-token latency rises to 577 ms: it favours
  starting new requests over continuing running ones. With the cache off it shows this already at c=16 (768 ms).

**From the server logs** (extracted into `results/raw/server_facts_phase1.json`; SGLang logs every 40th batch, so these count
logged lines, not all batches).
* SGLang captured its decode CUDA graphs only for batch sizes 1, 2, 4, 8. Every logged decode batch with at most 8 running
  requests used a graph (273 of 273 with the cache on, 255 of 255 off); **none of the 45 logged batches with more than 8 running
  requests did**, in either configuration. Its inter-token latency is 13 ms at c<=4 and 31-57 ms at c>=16, which fits that; the
  follow-up below tests it (graphs up to batch 32 bring that latency to 14-19 ms).
* The two schedulers' per-step token budgets match by default: 2,048 for vLLM on a GPU this size (read from its source, not logged
  at runtime) and a 2,048-token prefill chunk for SGLang (logged). I had suspected a mismatch and checked.
* SGLang's KV pool reached 99% usage with the cache off and 75% with it on. With the cache on, 2,068 of its 2,717 prefill batches
  reused at least 1,000 cached tokens (0 of 4,691 with it off).

**Guesses (not tested).**
* vLLM's inter-token spikes may come from image encoding and prefill sharing a step with decodes.
* The SGLang regression at c=16 may be scheduling or memory pressure around cache-hit requests.
* (Tested in the follow-up and *not* supported: that SGLang's Triton attention backend or its small CUDA-graph range explains its
  low throughput.)

### Caveats: read these before quoting the comparison

1. **The engines are still not configured identically** (see `NOTES.md`): different KV capacity (57,168 vs 50,728 tokens),
   different PyTorch versions, and a different vision-encoder attention backend (vLLM's log says FlashAttention for it; SGLang was
   launched with `--mm-attention-backend sdpa`). The follow-up tried SGLang with FlashInfer attention and CUDA graphs up to batch
   size 32, and the gap stayed. So the claim is "vLLM beat SGLang on this workload and this GPU, including SGLang's FlashInfer
   configuration", **not** "vLLM is faster in general", and I did not test other SGLang options (for example its vision-encoder
   attention backend or scheduling policy).
2. **The GPU's power state is not controlled, and it changes throughput.** One laptop GPU on one day. Phase 1 recorded no temperature
   or power. In the follow-up, median power draw ranged from 28 W to 55 W between runs and peak temperature from 69 to 92 C; within
   one cell (SGLang Triton, c=32) throughput rose from 1.18 to 1.57-1.64 req/s, about 35%, when power went from 28 W to 52-55 W
   (`scripts/gpu_state_by_run.py`). A rerun of vLLM's c=16 cell gave 3.07 req/s against 3.52 in Phase 1 (13% lower). Repeats within
   one session look tight; sessions are not equivalent. Gaps of a few tens of percent should not be over-read. (The SM clock
   reading is useless under WSL2: it reports 180 MHz at 100% utilisation, so clocks are not reported.)
3. Trace accuracy (about 56-59%) is below the zero-shot accuracy (63-64%), consistently across all four configurations, so it
   does not come from an engine. But the trace uses different images and far fewer requests, the intervals overlap, and I did not
   run the zero-shot prompt on the trace images. I cannot say how much of the gap is the added system prompt, few-shot turns
   and history that the policy never saw in training.
4. The synthetic task and trace are small and templated; cache hit rates here (about 66%) depend on how much the sessions share.

* **Graph coverage fixes SGLang's inter-token latency, not its throughput.** With graphs up to batch 32, ITL at c=16 falls from

  first token did not fall. So decode was not what limited SGLang here; waiting to *start* requests (time to first token of 8-19 s
  at c>=16, against vLLM's 2-3 s) was.
* **FlashInfer attention did not help.** B is no faster than Phase 1's Triton run at c=1 and c=4 (1.67 and 1.76 vs 1.69 and 1.75 req/s)
  and slower at c=16 and c=32 (1.15 and 1.09 vs 1.40 and 1.29). B ran in the GPU's high-power state throughout (50-55 W, 87-92 C), so
  a low-power state does not explain this.
* **vLLM kept its lead:** about 1.4x at c=1, 1.8x at c=4, and 3.1x and 3.3x at c=16 and c=32 against B (ratios of medians; the Phase 1

* **Phase 1 did not reproduce exactly:** vLLM's c=16 cell ran 13% lower (3.07 vs 3.52 req/s) and its time to first token 37% higher
  (3.03 vs 2.21 s) in the rerun. The ordering of the engines did not change.
* **What I still cannot explain** is why SGLang's time to first token is so much higher under load. Not tested: its vision-encoder
  attention backend (`sdpa` here), its scheduling policy, its multimodal preprocessing, and different KV-cache accounting.

## Phase 2 results: a prefix-aware router in Rust

`router/` is a standalone Rust service (tokio, axum, reqwest) that sits in front of OpenAI-compatible replicas. It hashes a request's
shared prefix (the system prompt and the few-shot turns; or an explicit `X-Prefix-Key` header) onto a consistent-hash ring with 160
virtual nodes per replica, with a bounded-load cap (a replica may hold at most 1.25x its fair share of in-flight requests, otherwise
the request spills to the next replica on the ring). It also has active health checks, header and idle timeouts, retries with
jittered exponential backoff, a per-replica circuit breaker, and a Prometheus `/metrics` endpoint. Round-robin and least-loaded
policies are built in for comparison. Details and the design choices are in `router/README.md`. Tests: 27 unit and 15 integration
tests (`cargo test`), the integration tests running the real router in front of mock replicas that can fail, hang, be killed and be

Setup for the measurements: two FP8 vLLM replicas of the merged checkpoint on the one RTX 5050 (they do not fit in bf16), each with a

### Prefix-aware vs round-robin

The result is mixed, and the run order turned out to matter more than the policy, so the first two runs are not the answer.

  cache; it says little about workloads with many prefixes.

## Phase 3 results: a fused RMSNorm + INT8 quantisation kernel in Triton

`servekernels/rmsnorm_int8.py` is one Triton kernel that does RMSNorm and per-row symmetric INT8 quantisation in a single pass,
registered as the PyTorch custom op `serving::rmsnorm_int8` (`torch.library.custom_op` + `register_fake`, checked with
`torch.library.opcheck`). For each row `y = x * rsqrt(mean(x^2) + eps) * weight` is computed in fp32, `scale = max|y| / 127`, and the
output is the int8 codes `rint(y / scale)` plus one fp32 scale per row. Unfused, RMSNorm writes `y` back to memory and the quantiser
reads it twice more; fused, the kernel reads `x` once and writes only int8 plus the scales. The Qwen2-VL-2B language model has 57 RMSNorms
(hidden size 1536, eps 1e-6): two per layer for 28 layers plus the final norm.

**What this phase is and is not.** The kernel is a standalone operator. It is **not wired into vLLM or SGLang**, and nothing in this
repo has an INT8 GEMM behind it, so there is **no end-to-end speed-up claim**. Two things are measured: how fast the operator runs
against PyTorch eager and `torch.compile`, and, for rule 4, what quantising every RMSNorm output to per-row INT8 does to click accuracy.

### Correctness

`tests/test_rmsnorm_int8.py` (48 tests; they need a CUDA GPU and Triton and are skipped elsewhere; run with `scripts/wsl/run_kernel_tests.sh`)
compares the kernel with an fp32 PyTorch reference for fp16, bf16 and fp32 over odd shapes (hidden sizes 1, 2, 33, 1000, 1536, 2049,
4096 and the 16384 maximum; 1 to 1025 rows), leading batch dimensions, strided and non-contiguous inputs, zero rows, constant rows,
fp16-overflow inputs (the squares overflow fp16; the kernel works in fp32), subnormals, a single huge outlier, a NaN in one row (it must
not leak into other rows), empty input, and invalid inputs; plus `torch.library.opcheck` and a `torch.compile(fullgraph=True)` run.
The scales must match to a relative 1e-5 and codes may differ by at most 1 (when fp32 summation order flips a rounding at a .5
boundary) on at most 0.1% of the codes. To check that the tests can fail, I broke the kernel on purpose (quantising with 126 instead of
127) and the suite failed. In the benchmark's own 36 cells the largest code difference from the reference was 1, on at most 7 in a
million codes, and the largest relative scale error was 3.4e-7.

### Roofline: how close to the memory-bandwidth limit

The operation is memory-bound (about 3 bytes moved per element for a handful of arithmetic operations), so the relevant ceiling is DRAM
bandwidth. The reference lines (measured on this GPU, except the two spec-based ones):

| ceiling | GB/s |
|---|---|
| measured copy 256MiB | 320 (262–321) |
| measured copy 64MiB | 262 (261–317) |
| measured read only 256MiB | 323 (323–344) |
| measured read only 64MiB | 239 (236–288) |
| reported spec peak (secondary source) | 384 |
| memory clock x bus width x 2, as the driver reports them | 384 |

The reported spec peak (384 GB/s: 128-bit GDDR7 at 24 Gbps) is a secondary-source figure for the laptop RTX 5050
([Wccftech](https://wccftech.com/nvidia-officially-launches-laptop-geforce-rtx-5050-gpu/amp/); another outlet printed 348, which looks like
a typo); the driver's own memory clock x bus width x 2 transfers per clock gives the same 384, but the factor of 2 is my assumption. The
measured ceilings (a device-to-device copy and a `sum()` that only reads, on a 256 MiB tensor) are what this GPU actually delivers in this setup.

Only cells that move at least 64 MiB are DRAM-bound (the L2 cache is 32 MiB). For those, the table compares the **best repeat** with the
best measured ceiling, because the GPU sat in different power and thermal states from repeat to repeat (next section) and a median across
states would compare unlike things:

| dtype | hidden | rows | MiB moved | fused GB/s, median (min–max) | best repeat GB/s | best vs reported spec peak | best vs best measured copy | best vs best measured read-only |
|---|---|---|---|---|---|---|---|---|
| bf16 | 1536 | 16384 | 72 | 258 (258–318) | 318 | 83% | 99% | 92% |
| bf16 | 4096 | 16384 | 192 | 265 (265–325) | 325 | 85% | 101% | 94% |
| bf16 | 8192 | 4096 | 96 | 316 (261–318) | 318 | 83% | 99% | 92% |
| bf16 | 8192 | 16384 | 384 | 269 (269–326) | 326 | 85% | 102% | 95% |
| fp16 | 1536 | 16384 | 72 | 314 (258–316) | 316 | 82% | 98% | 92% |
| fp16 | 4096 | 16384 | 192 | 322 (266–325) | 325 | 85% | 101% | 94% |
| fp16 | 8192 | 4096 | 96 | 261 (261–318) | 318 | 83% | 99% | 92% |
| fp16 | 8192 | 16384 | 384 | 269 (268–326) | 326 | 85% | 102% | 95% |

So at best the kernel reaches 316-326 GB/s: **82-85% of the reported spec peak, about the same as the best measured copy (98-102%), and
92-95% of the best read-only ceiling**. Over 100% against the copy line is not a contradiction: a copy moves equal read and write traffic,
this kernel moves two bytes in for each byte out. The medians are lower (258-322 GB/s) because of the throttling. Smaller cells are not at
the roofline: at 1-16 rows the time is a floor of about 0.006 ms that `torch.compile` hits too (launch cost and timer resolution), and one
program per row means a single row uses one of the GPU's 20 SMs. I did not tune `num_warps` or try several rows per program; the launch
configuration is a fixed heuristic.

**Why it beats eager** is plain from how the baseline is written: it is a chain of separate PyTorch ops that write fp32 intermediates to memory
(at 1 row eager takes about 0.17-0.22 ms against 0.006 ms fused, which is that chain's launch overhead); I did not count the kernels it launches.
**Why it beats `torch.compile`** by 1.4x-2.6x at 1024+ rows I have not established: I did not inspect inductor's generated kernels. A
plausible but untested explanation is that inductor does the two row reductions (sum of squares, abs-max) in separate loops or kernels.

### Measurement caveats

* **The GPU was power-capped and throttled.** Median power was 66-67 W, temperature reached 83-89 C, and NVML reported throttle reasons 0x4
  (software power cap) and, from repeat 2, 0x20 (software thermal slowdown). The same copy benchmark gave 262-264 GB/s in repeats 1-2 and
  320-321 GB/s in repeats 3-5. Timings are bimodal across repeats, which is why many cells have a median close to the max. The ratios between
  implementations are robust to this (measured back to back inside a cell); the "% of ceiling" numbers are not, hence the best-repeat table.
  `nvidia-smi` reports the SM clock as 180 MHz in every sample under WSL, which cannot be right at 67 W, so I do not use it.
* **Timer resolution.** `do_bench` times below about 0.02 ms come in steps of about 0.002 ms (0.0057, 0.0078, 0.0099 ms ...), so the small
  cells' ratios are coarse. The CUDA-graph timings resolve them better.
* **CUDA-graph numbers are not DRAM numbers for small tensors.** `do_bench_cudagraph` does not flush L2, so an operation moving 19-25 MB stays
  cache-resident and reaches about 560-670 GB/s, above the 384 GB/s peak. They are L2-warm GPU time, not a roofline.
* **`do_bench` and `do_bench_cudagraph` disagree by about 20% at the largest cells** (1.50 ms vs 1.22 ms for 8192 x 16384 fp16). I do not
  know why (the cache flush leaving dirty lines to write back is a guess).
* One GPU, one machine, one driver; no run on another GPU.

### Accuracy with INT8-quantised RMSNorm outputs (rule 4)

Because the kernel is not in an engine, there is no served model whose clicks it could change. To still follow the rule,
`scripts/kernel_accuracy.py` replaces the output of all 57 RMSNorms in the merged model by `dequantise(quantise(RMSNorm(x)))` ("fake
quantisation": activations only, weights stay bf16, no INT8 GEMM) and runs the same greedy HF decoding on both fixed sets. Three conditions
run in one process so only the norm differs: the model's own RMSNorm (baseline), the Triton kernel, and the fp32 PyTorch reference quantiser
(which the kernel should match). The pass rule was fixed before the run: |delta| <= 2.0 points and an exact sign test on the paired
discordant items with p > 0.05.

| set | n | baseline acc (95% CI) | kernel acc (95% CI) | fp32-reference quantiser acc | delta (kernel - baseline) | only baseline right / only kernel right | sign-test p | identical text, kernel vs baseline | identical text, kernel vs reference | verdict |
|---|---|---|---|---|---|---|---|---|---|---|
| synth300 | 300 | 64.00% (58.42%–69.22%) | 64.67% (59.10%–69.86%) | 63.00% | +0.7 pts | 5 / 7 | 0.774 | 42.67% | 43.33% | PASS |
| screenspot400 | 400 | 53.50% (48.60%–58.33%) | 52.00% (47.11%–56.85%) | 53.75% | -1.5 pts | 11 / 5 | 0.210 | 40.00% | 38.50% | PASS |

Both sets pass, but read that for what it supports. The sets cannot resolve a change of a few points: the 95% intervals are about 10
points wide, and with 12 and 16 discordant items the sign test has little power. **"No change was detected" is the claim; "no change" is
not.** Two more things are visible. First, the output text moved a lot: only 40-43% of the kernel's outputs are character-identical to
the baseline's (coordinates shift by a few units, e.g. `(535,574)` becomes `(535,572)`), against 56.3% and 54.5% identical for adapter vs merged
in the Phase 0 check, where the two models are the same function up to rounding. Second, the kernel and the fp32 reference quantiser
should be nearly the same function (codes differ in at most 7 in a million positions), yet their accuracies differ by 1.7 points on both
sets (64.67% vs 63.00% and 52.00% vs 53.75%) and only 38-43% of their outputs are identical. In bf16, a tiny change in one norm propagates
through 28 layers and changes greedy decodes, so differences of that size are **the noise floor of this evaluation**, not an effect of the
kernel. The activation error on real inputs is moderate: relative L2 error 0.026 on average over the 57 norms and 0.055 at worst (the last
layer's post-attention norm), measured on 16 synthetic items. The baseline here (53.50% on ScreenSpot) differs from the Phase 0 merged
model's 53.75% because this run used transformers 5.19.0 in the vLLM venv on Linux, the Phase 0 check transformers 5.20.2 on Windows.

### Limitations of Phase 3

* Not integrated into any engine: no end-to-end latency or throughput claim, and INT8 would only pay off with INT8 GEMMs behind it, which this repo does not have.
* The accuracy check is fake quantisation of the norm outputs only; it says nothing about quantising weights or other activations, and per-row scales are
  one design choice among several.
* One whole row per program: hidden sizes above 16384 are rejected, there is no backward (the quantiser is not differentiable), no bias or fused residual add,
  and no tuning of the launch configuration.
* The benchmark's baselines are same-math fp32 eager and `torch.compile` of it; a hand-written bf16 module or another fused library kernel was not tried.
* Results come from a throttled laptop GPU and are bimodal across repeats; the explanation for the `do_bench`/CUDA-graph gap and for the margin over `torch.compile` is not established.
* Triton 3.7.1 and torch 2.13 in the vLLM venv; the `sgym` venv (Triton 3.6) was not tested.

## Phase 4 results: prefill/decode disaggregation (a one-GPU attempt)

**What this is and is not.** Disaggregated serving puts prompt processing (prefill) and token generation (decode) on different GPUs and ships each
request's KV cache between them. I have one GPU, so this is **not** a two-GPU measurement. Two parts were done: an **analytical estimate** of the transfer
cost (labelled as an estimate everywhere), and a **measured one-GPU run** in which a prefill instance and a decode instance of vLLM share the 8 GB GPU and pass
the KV cache through **files on disk** with vLLM's `ExampleConnector`. The two instances still compete for the same compute and memory bandwidth, and the
transfer is a disk write and read, not NVLink, PCIe peer-to-peer or RDMA. What the run does show is whether the disaggregated path works end to end on this
stack, what it costs here, and where it breaks. A real two-GPU run (for example on Kaggle's two T4s) was not done.

### 1. Analytical estimate of the KV transfer (ESTIMATE, not a measurement)

KV cache per token = 2 (K and V) x 28 layers x 2 KV heads x 128 dims x 2 bytes (bf16) = 28,672 bytes, from the model's config. The trace's token counts
(measured with the real processor) give 1,666 tokens for a session's first turn, so about 45.6 MiB per request. Time at each link's *theoretical line rate*
(a lower bound: no protocol overhead, no overlap with compute, no copies):

| prompt | tokens | KV dtype | KV size (MiB) | link | line rate (GB/s) | time at line rate (ms) | as a share of the reference TTFT |
|---|---|---|---|---|---|---|---|
| first turn of a session | 1666 | bf16 | 45.6 | PCIe 3.0 x16 | 15.75 | 3.0 | 0.4% |
| first turn of a session | 1666 | bf16 | 45.6 | PCIe 4.0 x16 | 31.51 | 1.5 | 0.2% |
| first turn of a session | 1666 | bf16 | 45.6 | 10 GbE | 1.25 | 38.2 | 5.4% |
| first turn of a session | 1666 | bf16 | 45.6 | 100 GbE | 12.50 | 3.8 | 0.5% |

Next to the measured median time to first token of 711 ms (vLLM, prefix caching off, 1 client, Phase 1; it mixes prompt sizes), moving the KV over PCIe 4.0 x16
would cost at least 0.2% of it, and over 10 GbE 5.4%. The estimate says the wire is not what makes disaggregation hard on a fast interconnect; it says nothing
about scheduling, memory or software overhead. The estimate's bytes-per-token is consistent with the measured files: the KV store held about 49.5 MiB per request
in the runs below, which at 28,672 bytes per token is about 1,810 tokens: the same order as the prompt lengths I counted for this trace (1,254 tokens for the shared prefix, 1,666 for a first turn, 1,861 for the last turn measured).

### 2. What was run

* **colocated:** one vLLM instance, FP8 weights, 0.8 GiB KV cache.
* **split:** a *prefill* instance (`kv_producer`) and a *decode* instance (`kv_consumer`), FP8 weights, 0.4 GiB KV cache each (the same total KV memory), joined by
  `ExampleConnector` writing safetensors files under `~/work/kvstore`, behind a small proxy (`servebench/disagg_proxy.py`, 8 tests) that sends each request to
  the prefill instance with `max_tokens=1` and then replays it on the decode instance, streaming that answer back. The proxy also empties the KV store between
  repeats, because a producer that finds KV for a prompt on disk loads it instead of computing it.
* The agent trace of Phase 1, concurrency 1, 4 and 16, max_num_seqs 8, max_model_len 3072, 3 rounds; the order of the two setups alternates each round (the lesson of Phase 2).

### 3. The first run failed under concurrency (default flags)

**Diagnosis (code reading plus experiments; the mechanism is my reading, not confirmed with the vLLM authors).** `ExampleConnector.build_connector_meta` stores a
new request's KV at the first step in which the request is scheduled, using the blocks allocated at that step, and names the file by a hash of the whole prompt.
If the scheduler schedules only part of a prompt in that step, the file holds fewer tokens than its name claims, and the decode instance later loads 1,248 tokens
into 1,664 slots. The gap, 416 tokens, is about one screenshot (a screenshot is on the order of 400 tokens here; a bare one-image request is 412), which suggests the last image was deferred to a
later step. With one client a whole prompt always fits in one step, which is why 1 client works. Supporting experiments: with chunked prefill disabled on the prefill
instance (`--no-enable-chunked-prefill --max-num-batched-tokens=4096`), 4 clients worked (263 of 263 requests, one diagnostic run, `explore_disagg_bench_20261030-181519.json`,
and 3 full rounds below), but 16 clients still failed with the same error; raising the per-step budget to 16,384 tokens made 16 clients complete.

### Limitations of Phase 4

* One GPU: prefill and decode compete for the same compute and memory bandwidth, so latency here says nothing about what two GPUs would give. A real two-GPU run was not done.
* The KV moves through disk files with an *example* connector (its source calls it a debug implementation); NIXL, Mooncake, LMCache or NCCL-based connectors were not tried.
* The default-flag failure is a limitation of this connector with this stack (vLLM 0.32.0), found and diagnosed here; it has not been reported upstream. The mechanism above is inferred, not proven.
* The workaround changes how prefill is scheduled, so the split rows are not a "default vLLM" measurement; the colocated rows keep the defaults.
* FP8 weights and a small KV cache (0.4 GiB per instance), as in Phase 2; one trace; at most 16 clients; 3 rounds.
* The comparison of the 16-client split run with the colocated run crosses two sessions.

## Rules this folder follows

1. Every number in a table comes from a raw JSON under `results/raw/`.
2. Every raw file embeds GPU, driver, CUDA, package versions, model hash, command line, date, seed, concurrency.
3. Benchmarks use >= 3 repeats and report median and min-max (a standard deviation over 3 points would mislead).
4. After every serving change, click accuracy is re-run on the synthetic set and the ScreenSpot subset.
5. If a tool will not run on this hardware, the failure is documented in `NOTES.md` and the phase is marked attempted.

In the Linux clone, with the vLLM venv (torch + Triton on the GPU; `pytest` installed into it with `uv pip install`):

## Reproduce Phase 0

```bash
pip install -r serving/requirements.txt                    # client tooling; the main repo's requirements are also needed
python serving/scripts/export_sets.py                      # renders synth300 + screenspot400 to PNG + manifest (on Windows)
python serving/scripts/merge_adapter.py --adapter runs/clean/adapter --out serving/models/merged-clean

python serving/scripts/merge_diff.py serving/results/raw/merge_verify_<timestamp>.json
python serving/scripts/gen_traces.py --name default --stats
pytest serving/tests
```

Images are rendered once on Windows because the synthetic generator uses installed fonts; rendering inside WSL2 would give
different pixels. PNGs are git-ignored (`serving/traces/*/images`, `serving/data/*/images`; the ScreenSpot subset is third-party
content); manifests and `trace.jsonl` carry sha256 checksums, and `servebench.data.verify_manifest` detects any difference.
The adapter weights and the merged checkpoint are not in the repo; the commands above recreate them.

## Limitations so far

* Only the `clean` adapter is served. The `biased` and `holdout` adapters are not merged or tested.
* The merge check is one deterministic greedy run per model per set; it measures merge rounding, not run-to-run variance.
* Base model revision hash was not recorded (offline HF cache lookup failed); the merged checkpoint is identified by its own
  hash.
* Phase 1 compares the engines in one configuration each; see its caveats before drawing a general conclusion.
