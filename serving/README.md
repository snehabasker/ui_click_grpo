# serving/: serving the trained click policy under agent-style traffic

Goal: take the LoRA policy from the main project, serve it, and measure what each serving technique buys, with
reproducible raw logs and an accuracy check after every change. A speed-up that changes click accuracy is reported as a
failure, not a win.

Nothing under `serving/` changes training code or the published results in `../results/`.

## Status

| Phase | What | Status |
|---|---|---|
| 0 | Merge adapter, verify it, trace generator, load client, tests | **done** (this document) |
| 1 | vLLM vs SGLang on the same checkpoint | **done, with caveats** (see Phase 1 results and the follow-up on SGLang's configuration) |
| 2 | Prefix-aware router in Rust | not started |
| 3 | Fused RMSNorm + INT8 quantisation Triton kernel | not started |
| 4 | Prefill/decode disaggregation (time-boxed) | not started |
| 5 | TensorRT-LLM (time-boxed) | not started |

Hardware: one RTX 5050 Laptop GPU (8 GB, compute capability 12.0, driver 592.82, CUDA 13.1 as reported by the driver),
Windows 11, 23.6 GB RAM. Engines run inside WSL2 Ubuntu (WSL 3.0.3, kernel 6.18, 11.7 GB of RAM visible to Linux).

## Phase 0 results

### 1. The merged checkpoint clicks like the adapter model

The LoRA adapter (`runs/clean/adapter`) was merged into the bf16 base weights, so every engine loads one plain checkpoint
(`merged-clean`, model hash `f4945dbb7c5b459fe0cce1b78362bff134b12a4a15108e9342c8c6b3a1d0de7f`). Both models were run through the
same HF code path, greedy, on the two fixed sets. Pass criteria were fixed before looking at results: accuracy within 2.0
points **and** an exact paired sign test with p > 0.05.

| set | adapter model | merged model | delta | only adapter / only merged correct | sign test p | verdict |
|---|---|---|---|---|---|---|
| synthetic held-out (n = 300) | 63.33% [57.7, 68.6] | 63.33% [57.7, 68.6] | +0.00 pts | 2 / 2 | 1.000 | pass |
| ScreenSpot subset (n = 400) | 53.25% [48.4, 58.1] | 53.75% [48.9, 58.6] | +0.50 pts | 3 / 5 | 0.727 | pass |

Accuracy is preserved, but the clicks are **not bit-identical**, because the merge rounds the LoRA delta into bf16 weights:

| set | identical click point | median shift | 90th percentile shift | largest shift |
|---|---|---|---|---|
| synthetic | 58.3% | 0 | 10 units (1.0% of the image side) | 98 units |
| ScreenSpot | 54.9% | 0 | 18.8 units (1.9%) | 725 units |

(units: the model's 0-1000 coordinates, worst axis, over items where both models returned a valid point.) A handful of items
move a long way in either direction (hit -> miss and miss -> hit both occur), and they cancel in the totals. This is a
reason to keep the accuracy check after every later change rather than assume equivalence.

The adapter model also reproduces the published numbers on the re-rendered images: 63.33% (190/300) on the synthetic set,
identical to `../results/eval_clean.json`, and 53.25% (213/400) on ScreenSpot against the published 53.2%.

Raw: `results/raw/merge_verify_20261026-004301.json`, `results/raw/merge_diff_20261026-004333.json`,
`results/raw/merge_info_clean.json`.

### 2. The agent trace

`serving/traces/default` (96 sessions, seed 0), generated by `scripts/gen_traces.py`:

| property | value |
|---|---|
| sessions / requests | 96 / 560 (3-8 turns per session) |
| sessions sharing a prefix | 72 (75%), over 4 shared prefixes with skewed popularity (33 / 18 / 12 / 9 sessions) |
| the other 24 sessions | a unique prefix each (differs from the first characters) |
| shared prefix | system prompt + 2 few-shot screenshots with their answers |
| history | previous instructions and answers as text (no old screenshots) |
| first turn incl. shared prefix | 1,666 tokens |
| a bare single-screenshot request | 412 tokens |
| shared prefix (difference of the two) | about 1,254 tokens, i.e. roughly 75% of a first-turn request is cacheable |

Token counts come from the real Qwen2-VL processor (`traces/default/token_stats.json`), not an estimate. The "bare request"
count uses the raw instruction without the fixed answer-format sentence, so the prefix figure is approximate.
Replays are identical across engines: the assistant history in every request is the ground-truth click, not the model's own
answer. Seeds are disjoint from training (< 1e6) and from the held-out test splits (>= 1e7).

Important: the policy was trained zero-shot with one screenshot. The trace adds a system prompt, few-shot turns and history,
which the policy never saw. Click accuracy *on the trace* is therefore reported separately from the zero-shot accuracy checks
and may differ; that is measured in Phase 1, not assumed here.

### 3. Load client and validation

`servebench/client.py` streams every request and records time-to-first-token, inter-token gaps, end-to-end latency, tokens
(from the engine's `usage`), throughput, click accuracy on the trace, GPU memory and utilisation (nvidia-smi, 0.5 s), and the
engine's prefix-cache counters from `/metrics` where they exist. Failures (timeouts, 5xx, resets) are recorded, never raised.

Its inter-token timing was checked against a raw-socket server with exact (busy-wait) spacing. Median gap, 72 gaps per row,
0 request errors:

| true spacing | raw-socket reader | this client |
|---|---|---|
| 10 ms | 10.03 ms | 10.03 ms |
| 20 ms | 20.06 ms | 20.05 ms |
| 40 ms | 40.08 ms | 40.10 ms |

So inter-token numbers from this client can be trusted in the 10-40 ms range where decode steps on this GPU are expected to
fall. (On this Windows machine `asyncio.sleep(3 ms)` actually sleeps 15.95 ms in that run, which is why the mock server cannot
validate small intervals.) Raw: `results/raw/client_timing_20261026-004655.json`. How this was found is in `NOTES.md`.

25 tests (`pytest serving/tests`) cover statistics, manifests and tamper detection, environment capture, trace determinism and
prefix sharing, message construction, and the client against a mock server. **The mock server only tests plumbing: no number
from it is ever reported** (its output files are prefixed `MOCK_`).

## Phase 1 results: vLLM vs SGLang

Both engines serve the same merged checkpoint (`merged-clean`) on the same GPU, each with prefix caching **on and off** (four
configurations). Each configuration: launch, click-accuracy check through the live server, then the trace replayed at client
concurrency 1, 4, 16, 32 with **3 repeats** per cell. Before every repeat the prefix cache and the multimodal (image) cache are
reset, and a short warm-up with unique prefixes is discarded. All 48 load-test runs finished with **0 request errors**. Every
number below comes from the raw files under `results/raw/` via `scripts/summarize.py`; the full tables (p99 latencies, GPU
memory) are in `results/tables/phase1.md`.

Low concurrency replays a **prefix of the same trace** (identical for both engines), because serial requests are slow:
c=1 uses the first 24 sessions (129 requests), c=4 the first 48 (263), c=16 and c=32 all 96 (560).
Cells show the median over 3 repeats, with min-max in brackets.

### Why: what is measured, what the logs show, and what is only a guess

**Measured.**
* Both caches work and hit about equally by volume (66-67% of prompt tokens). So the engines differ in *what they do with* a hit,
  not in whether they get one. (SGLang's own log agrees; see below. The shared prefix is about 1,250 tokens, from
  `traces/default/token_stats.json`.)
* For vLLM the cache is worth a lot at every concurrency: with it off, each request recomputes the whole prompt, which is
  1,666 tokens on a first turn.
* For SGLang the cache helps at c=1 and c=4 and does nothing or hurts at c=16 (throughput 1.60 -> 1.40, TTFT 5.57 -> 8.63 s).
* vLLM's time to first token stays low at c=32 with the cache on (2.03 s) but its inter-token latency rises to 577 ms: it favours
  starting new requests over continuing running ones. With the cache off it shows this already at c=16 (768 ms).

**From the server logs** (extracted into `results/raw/server_facts_phase1.json`; SGLang logs every 40th batch, so these count
logged lines, not all batches).
* SGLang captured its decode CUDA graphs only for batch sizes 1, 2, 4, 8. Every logged decode batch with at most 8 running
  requests used a graph (273 of 273 with the cache on, 255 of 255 off); **none of the 45 logged batches with more than 8 running
  requests did**, in either configuration. Its inter-token latency is 13 ms at c<=4 and 31-57 ms at c>=16, which fits that; the
  follow-up below tests it (graphs up to batch 32 bring that latency to 14-19 ms).
* The two schedulers' per-step token budgets match by default: 2,048 for vLLM on a GPU this size (read from its source, not logged
  at runtime) and a 2,048-token prefill chunk for SGLang (logged). I had suspected a mismatch and checked.
* SGLang's KV pool reached 99% usage with the cache off and 75% with it on. With the cache on, 2,068 of its 2,717 prefill batches
  reused at least 1,000 cached tokens (0 of 4,691 with it off).

**Guesses (not tested).**
* vLLM's inter-token spikes may come from image encoding and prefill sharing a step with decodes.
* The SGLang regression at c=16 may be scheduling or memory pressure around cache-hit requests.
* (Tested in the follow-up and *not* supported: that SGLang's Triton attention backend or its small CUDA-graph range explains its
  low throughput.)

### Caveats: read these before quoting the comparison

1. **The engines are still not configured identically** (see `NOTES.md`): different KV capacity (57,168 vs 50,728 tokens),
   different PyTorch versions, and a different vision-encoder attention backend (vLLM's log says FlashAttention for it; SGLang was
   launched with `--mm-attention-backend sdpa`). The follow-up tried SGLang with FlashInfer attention and CUDA graphs up to batch
   size 32, and the gap stayed. So the claim is "vLLM beat SGLang on this workload and this GPU, including SGLang's FlashInfer
   configuration", **not** "vLLM is faster in general", and I did not test other SGLang options (for example its vision-encoder
   attention backend or scheduling policy).
2. **The GPU's power state is not controlled, and it changes throughput.** One laptop GPU on one day. Phase 1 recorded no temperature
   or power. In the follow-up, median power draw ranged from 28 W to 55 W between runs and peak temperature from 69 to 92 C; within
   one cell (SGLang Triton, c=32) throughput rose from 1.18 to 1.57-1.64 req/s, about 35%, when power went from 28 W to 52-55 W
   (`scripts/gpu_state_by_run.py`). A rerun of vLLM's c=16 cell gave 3.07 req/s against 3.52 in Phase 1 (13% lower). Repeats within
   one session look tight; sessions are not equivalent. Gaps of a few tens of percent should not be over-read. (The SM clock
   reading is useless under WSL2: it reports 180 MHz at 100% utilisation, so clocks are not reported.)
3. Trace accuracy (about 56-59%) is below the zero-shot accuracy (63-64%), consistently across all four configurations, so it
   does not come from an engine. But the trace uses different images and far fewer requests, the intervals overlap, and I did not
   run the zero-shot prompt on the trace images. I cannot say how much of the gap is the added system prompt, few-shot turns
   and history that the policy never saw in training.
4. The synthetic task and trace are small and templated; cache hit rates here (about 66%) depend on how much the sessions share.

**What this shows**

* **Graph coverage fixes SGLang's inter-token latency, not its throughput.** With graphs up to batch 32, ITL at c=16 falls from
  51.4 ms to 17.7 ms (Triton, A) or 14.4 ms (FlashInfer, B), comparable to vLLM's 17.6 ms. But throughput did not improve and time to
  first token did not fall. So decode was not what limited SGLang here; waiting to *start* requests (time to first token of 8-19 s
  at c>=16, against vLLM's 2-3 s) was.
* **FlashInfer attention did not help.** B is no faster than Phase 1's Triton run at c=1 and c=4 (1.67 and 1.76 vs 1.69 and 1.75 req/s)
  and slower at c=16 and c=32 (1.15 and 1.09 vs 1.40 and 1.29). B ran in the GPU's high-power state throughout (50-55 W, 87-92 C), so
  a low-power state does not explain this.
* **vLLM kept its lead:** about 1.4x at c=1, 1.8x at c=4, and 3.1x and 3.3x at c=16 and c=32 against B (ratios of medians; the Phase 1
  vLLM rows and the follow-up B rows come from different sessions, so these carry the session-to-session variation described in
  the caveats, which is far smaller than the gap at c >= 16).
* **Phase 1 did not reproduce exactly:** vLLM's c=16 cell ran 13% lower (3.07 vs 3.52 req/s) and its time to first token 37% higher
  (3.03 vs 2.21 s) in the rerun. The ordering of the engines did not change.
* **What I still cannot explain** is why SGLang's time to first token is so much higher under load. Not tested: its vision-encoder
  attention backend (`sdpa` here), its scheduling policy, its multimodal preprocessing, and different KV-cache accounting.

### Remaining follow-ups (not done)

1. Repeat the whole comparison on a second day with the GPU power state recorded, ideally with a cooled laptop.
2. Run the zero-shot prompt on the trace images to separate the prompt-context effect on accuracy.
3. Try SGLang's vision-encoder attention backend and scheduling options to find where its time to first token goes.

## Rules this folder follows

1. Every number in a table comes from a raw JSON under `results/raw/`.
2. Every raw file embeds GPU, driver, CUDA, package versions, model hash, command line, date, seed, concurrency.
3. Benchmarks use >= 3 repeats and report median and min-max (a standard deviation over 3 points would mislead).
4. After every serving change, click accuracy is re-run on the synthetic set and the ScreenSpot subset.
5. If a tool will not run on this hardware, the failure is documented in `NOTES.md` and the phase is marked attempted.

```bash
python serving/scripts/gen_traces.py --name default --stats
pytest serving/tests
```

Images are rendered once on Windows because the synthetic generator uses installed fonts; rendering inside WSL2 would give
different pixels. PNGs are git-ignored (`serving/traces/*/images`, `serving/data/*/images`; the ScreenSpot subset is third-party
content); manifests and `trace.jsonl` carry sha256 checksums, and `servebench.data.verify_manifest` detects any difference.
The adapter weights and the merged checkpoint are not in the repo; the commands above recreate them.

## Limitations so far

* Only the `clean` adapter is served. The `biased` and `holdout` adapters are not merged or tested.
* The merge check is one deterministic greedy run per model per set; it measures merge rounding, not run-to-run variance.
* Base model revision hash was not recorded (offline HF cache lookup failed); the merged checkpoint is identified by its own
  hash.
* Phase 1 compares the engines in one configuration each; see its caveats before drawing a general conclusion.
